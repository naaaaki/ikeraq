## 1. サイト名とコンセプト

### 1.0 サイト名：Wakuru（ワクル）★v0.6 で決定

| 項目 | 内容 |
|---|---|
| **サイト名** | Wakuru |
| **読み** | ワクル |
| **ドメイン** | `wakuru.dev`（第一候補） |
| **由来** | 「**わかる**」＋「**ワクワク**」 |

**由来の意味:**

- **わかる** — 何ができるリポジトリなのかが**わかる**サイト。機能そのもの
- **ワクワク** — 新しいものを見つける感情。体験そのもの

**選定理由:**

1. **読みが一意**（ワクル以外に読めない）。指名検索が割れない
2. **完全な造語**。Web検索した範囲で既存サービスとの衝突が確認されなかった
3. 3モーラで打ちやすく、覚えやすい
4. 意味が二重に効いており、日本語話者に直接届く

> **⚠️ 公開前に必ず確認すること**
> - `wakuru.dev` の空き状況
> - J-PlatPat（特許庁）での商標検索
> - GitHub / npm / X での `wakuru` 検索
> - X のハンドル取得可否
>
> 検索した範囲で衝突は見つからなかったが、**保証はできない**。

### 1.1 「IT系サイト」であることの伝え方

**名前自体はIT系だと分からなくてよい。** Zenn / Qiita / Notion / Vercel / Slack /
Product Hunt — いずれも名前だけではIT系だと分からない。
これは意図的に受け入れた設計判断である。

代わりに、以下でIT系であることを伝える。

| 手段 | 内容 |
|---|---|
| **TLD** | `.dev` はGoogleが管理する開発者向けTLD。エンジニアには一瞬で伝わる |
| **title タグ** | `Wakuru | GitHubで話題のリポジトリを日本語で` |
| **タグライン** | 「新しい技術が、わかる。」 |
| **ロゴ・デザイン** | 技術サイトらしいトーン（Phase 3 で作り込む） |

> **補足:** ブランド名・ドメインに `github` は使えない（GitHub商標ポリシー）が、
> **title タグや説明文には使用できる**。検索キーワードはここで回収する。

### 1.2 コンセプト

**「偽スターを見抜く、日本語のGitHubトレンド」**

### 根拠

Carnegie Mellon 大学らの査読論文 *"Six Million (Suspected) Fake Stars on GitHub"*
（ICSE 2026 採択、arXiv:2412.13459 v2）によれば:

- 2019年7月〜2024年12月に **約600万個の偽スター**、18,617リポジトリでの
  偽スターキャンペーン（約30万1千アカウント関与）を検出
- 2024年7月のピーク時、**50スター以上のリポジトリの16.66%** が偽スターに関与
- 偽スターの最大の受益カテゴリ（マルウェア以外）は **AI/LLM分野**

つまり「スター数を見て判断する」ことが最も危険なのが、いま最もトレンドに入る分野。
**ここに警告を出せるサイトは日本語圏に存在しない。**

### 差別化の三層

| 層 | 内容 | 競合の状況 | 実装 |
|---|---|---|---|
| 第1層 | 偽スター・健全性の警告 | **両競合になし** | **Phase 1** |
| 第2層 | ライセンス・メンテ状況の一覧表示 | 一部あり（詳細ページのみ） | Phase 1 |
| 第3層 | 日本語の警告・ラベル表示・鮮度 | 両競合が実施済み | Phase 1 |

**第3層だけでは勝てない。第1層が本サイトの存在理由。**
したがって **第1層は Phase 1 で必ず実装する**（v0.2 では Phase 2 送りになっており、
「Phase 1 の時点で差別化がない」という矛盾があった。v0.3 で修正）。

## 2. 【最重要】SEOリスク管理

### 2.1 何が問題か

Google は 2024年3月に **scaled content abuse（大規模なコンテンツの不正使用）** を
正式なスパムポリシーとして導入した。公式定義（Search Central）:

> 検索順位の操作を主目的として、ユーザーの役に立たない多数のページを生成すること。
> **自動生成・人力・その両方の組み合わせのいずれであるかを問わない。**

公式に挙げられている該当例:
- 生成AI等で、ユーザーへの価値を付加せずに多数のページを生成する
- **人間によるレビューやローカライズなしに、自動翻訳のみでページ化する**

2024年3月の適用時、数百サイトが順位降格ではなく **インデックス削除** された。

### 2.2 本サイトが直撃する理由

「全トレンドリポジトリの個別ページを自動生成する」設計は以下の点で該当リスクが高い:

- ページの主要コンテンツが「英語descriptionの翻訳＋AI要約」＝独自価値が薄い
- 大量・自動・高速に生成される
- READMEの転載比率が高いと、別途「scraping（他サイトの実質コピー）」にも抵触

**この設計のまま公開すると、収益化どころかサイトごと消える可能性がある。**

### 2.3 対策（必須要件）

| # | 対策 | 実装 |
|---|---|---|
| S1 | **全件を個別ページ化しない** | 生成基準を満たしたものだけページ化（§2.4） |
| S2 | **1ページに独自データを必ず載せる** | 偽スター判定・健全性スコア・スター推移・ライセンス商用可否・警告理由 |
| S3 | **注目枠には人間の一言を必ず入れる** | ただし件数は §17 の運用ルールに従う（毎日大量に書かない） |
| S4 | **README全文を載せない** | 抜粋は最大500字。著作権対策も兼ねる（§8） |
| S5 | **独自価値の乏しいページは noindex** | 判定は §2.5。**usability_score とは連動させない** |
| S6 | **翻訳だけのページを作らない** | description翻訳のみのページは作成禁止 |

### 2.4 個別ページの「生成」基準

以下の **いずれか** を満たすもののみ個別ページを生成する。

- スター数 1,000 以上
- 日次スター増加 300 以上
- **警告フラグが1つ以上立っている**（＝注意喚起に価値がある）
- 手動で「注目」指定したもの

**満たさないものは一覧ページに行として載せるだけ。個別ページは作らない。**

想定生成数: **1日 5〜15ページ程度**。

### 2.5 個別ページの「index」判定 ★v0.3 で分離

> **v0.2 の矛盾:** 「警告フラグが立つ→ページ生成」かつ
> 「usability_score が低い→noindex」という設計だったため、
> **警告つきリポジトリはページが作られると同時に noindex される**という循環があった。
> 警告つきこそ本サイトが見せたいコンテンツなので、これは致命的な誤り。

**生成と index は別の判定とする。**

| 条件 | index |
|---|---|
| 警告フラグあり（`fake_star_suspicion` が low 以上を含む） | ✅ **index する**（本サイト固有の価値） |
| 手動コメント（`human_note`）あり | ✅ index する |
| スター推移グラフが表示できる（7日以上のデータあり） | ✅ index する |
| **上記いずれも該当せず、内容が description の翻訳と定型データのみ** | ❌ **noindex** |

判定式:

```
is_indexable =
    flags.length > 0
 || fake_star_suspicion != "none"
 || human_note != null
 || snapshot_days >= 7
```

**usability_score は index 判定に使わない。**
低スコア＝価値がない、ではなく、低スコアであること自体が読者への情報だからである。

### 2.6 監視指標（危険信号）

Search Console で以下を週次で確認する。異常時は即座に S5 を強化する。

- インデックス率の急落
- 「クロール済み - インデックス未登録」の急増
- 手動による対策の通知

## 3. ターゲットと収益設計

### ターゲット読者

- 日本語圏のソフトウェアエンジニア
- 「Xで流れてきたリポジトリが何なのか、3分で知りたい」層
- **業務での採用可否を判断したい層（本命）**

### 収益モデル（複線化）

**重要な前提: AdSense 単体は成立しない。**

Stack Overflow の "State of Developer Engagement Report" によれば、
**開発者の広告ブロック利用率は 72%**（一般ネットユーザーは 11%）。
同調査で開発者の 62% が「広告が理由でサイト訪問をやめた経験がある」と回答。

| # | 手段 | 優先度 | 備考 |
|---|---|---|---|
| 1 | **ニュースレター → スポンサー枠** | 高（中長期の本命） | TLDR は1号3枠・1枠 $5,000〜$15,000 規模 |
| 2 | 技術書・クラウド・スクールのアフィリエイト | 高 | 文脈連動 |
| 3 | 求人・転職サービス連携 | 中 | 読者層と親和性が高い |
| 4 | GitHub Sponsors / 有料版・API提供 | 低 | 実績が出てから |
| 5 | AdSense | 補助 | **収益計画に含めない** |

日本の技術系個人ブログの現実的な到達点は **1年で月数千円〜3万円**程度。
**最初の3〜6ヶ月はほぼ収益ゼロと想定しておくこと**（§17.3 参照）。

→ **本サイトの資産は「日次スナップショットの蓄積データ」そのもの**。

## 4. 更新頻度の設計（収集と公開の分離）

### 4.1 実態の把握

競合の週次記事における新規エントリー率は **20件中18件（第26週）、22件中16件（第25週）**。
週単位では 8〜9割が入れ替わる。

日次の新規は **10〜15件程度** と推定される（※要実測。Phase 0 で確定させる）。

### 4.2 頻度の設計

| 処理 | 頻度 | 実行者 |
|---|---|---|
| **データ収集・スナップショット保存** | **毎日** | **自動（人間の負担ゼロ）** |
| 一覧ページの更新 | 毎日 | **自動** |
| 個別ページの生成 | 生成基準を満たした時点で随時 | **自動** |
| 手動コメント（注目枠） | 週1〜2回まとめて | 人間 |
| 週次サマリ（潮流分析） | 週1 | 人間（Claude Code と対話しながら） |

**「毎日」なのはマシンであって人間ではない。** 詳細は §17。

「毎日更新」の本質的価値は記事量ではなく、
**①新規検知の速さ ②スター速度データの蓄積**（＝偽スター判定の基盤）。

## 7. スコアリング仕様

> **v0.3 の重要な変更:**
> スコアを **2軸に分離** した。
> - `usability_score` = **実運用に耐えるか**（ライセンス・メンテ状況）
> - `fake_star_suspicion` = **数字が信用できるか**（偽スターの疑い）
>
> v0.2 では `star_spike` が `usability_score` に混入しており、
> 「AGPLだから使いにくい」と「スターが怪しい」が同じ数字に潰れていた。

### 7.1 警告フラグ

| フラグ | 条件 | 軸 | 表示 |
|---|---|---|---|
| `stale` | `pushed_at` が180日以上前 | 実運用 | ⚠ メンテ停止の疑い |
| `archived` | `is_archived == true` | 実運用 | ⛔ アーカイブ済み |
| `no_license` | ライセンス未設定 | 実運用 | ⛔ 利用条件不明（原則利用不可） |
| `copyleft` | AGPL / GPL 系 | 実運用 | ⚠ 自社サービス組込み注意 |
| `thin_readme` | `readme_length < 500` | 実運用 | ⚠ ドキュメント不足 |
| `abnormal_fork_ratio` | `forks / stars > 0.5` | 偽スター | ⚠ 数値に不自然さあり |
| `too_new` | `created_at` が30日以内 かつ stars > 5,000 | 偽スター | ⚠ 急成長・実績未知数 |
| `star_spike` | 日次スター増加が過去7日平均の10倍超 | 偽スター | ⚠ スター急増（要確認） |
| `low_activity` | スター数に対し fork・Issue・contributor が極端に少ない | 偽スター | ⚠ 活動量に対しスターが多い |
| `duplicate_suspect` | 同名/類似名が同期間に複数 | 偽スター | ⚠ 類似リポジトリ複数あり |

**誤検知に注意すべきフラグ:**

- `abnormal_fork_ratio` — **学習教材系リポジトリでは正常に発生する**
  （例: `CS-Fundamentals` のような教材は fork されるのが前提）。
  カテゴリが `learning` の場合は閾値を緩めるか、フラグを抑制すること。
- `thin_readme` — 単機能ライブラリでは正常。強い警告にしない。

### 7.2 偽スター疑いの判定（差別化の核・Phase 1 で実装）

論文 StarScout が用いるシグナルを、GitHub API で取得できる範囲で簡易再現する。

| シグナル | 実装 | 依存 |
|---|---|---|
| **スター速度の異常** | `daily_snapshots` から急増を検出（`star_spike`） | スナップショット7日分 |
| **低活動** | スター数 vs fork・Issue・contributor の比率（`low_activity`） | REST APIのみ |
| **新規性** | `created_at` が新しいのにスターだけ多い（`too_new`） | REST APIのみ |
| **実利用の欠如** | `dependents_count` または代替（§7.5） | **要検証** |

合成して `fake_star_suspicion` を `none` / `low` / `medium` / `high` に分類。

```
該当シグナル数 0 → none
              1 → low
              2 → medium
              3以上 → high
```

**表記は必ず「疑い」に留める。断定しない。**
論文自体が "suspected" と表現しており、ヒューリスティックには誤検知がある。
断定表現は名誉毀損リスクを生む。

表示例:
> ⚠ スター数の伸び方に不自然な点があります（急増・低活動）。
> これは自動判定であり、偽スターと断定するものではありません。判定基準

### 7.3 コールドスタート対策 ★v0.3 で新設

`star_spike` は「過去7日平均」を必要とするため、
**運用開始から7日間は判定できない。**

対策（両方実施）:

1. **Phase 0 で7〜14日間、データ収集のみ行う助走期間を設ける**（§13 Phase 0）
   公開時点で全リポジトリに7日以上の履歴がある状態にする。
2. **履歴が不足しているリポジトリには代替判定を使う**

```
snapshot_days < 7 の場合:
  平均増加率 = stars / (今日 - created_at の日数)
  この値と直近増加を比較して代用する
  ただし信頼度を下げ、表示は「判定中」とする
```

新規に検知したリポジトリは常にこの状態になるため、
**恒久的に必要なロジック**である（Phase 0 だけの問題ではない）。

### 7.4 usability_score（0-100）★実運用可否のみ

```
基準点 100
  - archived               -50
  - no_license             -40
  - stale                  -30
  - copyleft               -15
  - thin_readme            -10
  （下限0）
```

**偽スター系のフラグはここに含めない**（別軸のため）。

**重み付けはTBD。運用しながら調整する前提。**
スコアは単独で表示せず、必ずフラグの内訳とセットで見せること。
`/about/criteria` で算出方法を全公開する。

> **注意:** OpenSSF Scorecard 自身が公式に
> 「集約スコアはヒューリスティックであり誤検知・見逃しがある」と注意喚起している。
> 本サイトも同様の但し書きを必ず表示する。この誠実さが信頼を生む。

### 7.5 `dependents_count` のフォールバック設計 ★v0.3 で新設

> **リスク:** GitHub の Dependency graph（"Used by" の数値）は
> **REST API / GraphQL では公式に提供されていない可能性が高い**（Web UI のみ）。
> v0.2 ではこの値に偽スター判定の1シグナルが依存していたが、
> 取得不可の場合の設計がなかった。

**Phase 0 で必ず検証すること。** 結果に応じて分岐する。

| 検証結果 | 対応 |
|---|---|
| 取得できる | そのまま `no_dependents` フラグとして使用 |
| **取得できない** | **以下の代替シグナルの合成で「実利用の欠如」を判定** |

代替シグナル（すべて REST API で取得可能）:

- `releases_count == 0`（リリースを1度も切っていない）
- `contributors_count <= 1`（作者以外の貢献者がいない）
- `open_issues == 0` かつ スター数が多い（誰も使っていない兆候）
- fork 数がスター数に対して極端に少ない

**スクレイピングで "Used by" を取りに行くことは推奨しない。**
§10 の方針（公式経路優先）に反し、かつ壊れやすいため。

### 8.1 ステマ規制（最優先）

2023年10月1日施行の景品表示法・指定告示（消費者庁）。

- アフィリエイトリンクを含むページには **「PR」「広告」「アフィリエイト広告を利用しています」** 等を、
  消費者が認識できる位置（**ファーストビュー**）に明示すること
- ランキング・比較コンテンツは特に厳格に見られる（本サイトはまさに該当）
- 処罰対象は原則「広告主」だが、掲載者も表記義務を負う

**実装: 全ページ共通ヘッダに表記を入れる。Phase 1 の初日から。**

### 8.2 README・descriptionの著作権

- READMEはコードとは別に、そのリポジトリのライセンスに従う
- **ライセンス未設定のREADMEは「全権利留保」**。全文転載は著作権侵害の恐れ
- GPL系READMEの大量転載はコピーレフト継承の議論も招く

**実装方針:**
- README全文は載せない（**抜粋は最大500字**）
- 事実データ（スター数・言語・ライセンス名・コミット日）は著作物性が低く、掲載可
- 要約は本サイトが生成した独自テキストとして扱う（＝内容の責任も本サイトが負う）
- 出典として GitHub への正規リンクを必ず設置

### 8.3 自動判定の免責

**本サイトは AI による文章生成を行わない**（§9.1）。
掲載されるのは GitHub API から取得した事実データと、
決定的ロジックによる判定結果のみである。

それでも判定ロジックに関する免責は必要:

- **「警告は自動判定であり、断定するものではない」と全ページに明示**
- ライセンス等の重要項目は GitHub API の構造化データから機械取得している旨を記載
- 判定基準は `/about/criteria` で全公開する
- 技術選定の最終判断は原典を確認するよう促す

> 週次サマリは人間が執筆するため、その内容の責任は運営者が負う。

### 8.4 その他

- プライバシーポリシー（アクセス解析・広告のCookie利用）必須
- 特商法表記は無料＋広告のみなら原則不要。有料版を始める際に追加

## 9. 技術スタック・アーキテクチャ

### 9.1 LLM は使わない ★v0.4 で確定

**日次パイプラインでは LLM を一切使用しない。**

| 項目 | 方式 |
|---|---|
| 日本語要約 | **実装しない** |
| カテゴリ分類 | ルールベース（§6.3） |
| 偽スター判定 | 決定的ロジック（§7.2） |
| ライセンス判定 | GitHub API の構造化データ |
| usability_score | 計算式（§7.4） |

**理由:**

1. **差別化の核（偽スター判定・ライセンス表示）は LLM を必要としない。**
   日次スナップショットの差分計算と GitHub API のデータだけで成立する。
2. ランニングコストが **ドメイン代のみ**になる。
3. 誤情報リスクがゼロになる。生成文がなければ、事実の誤りは起こらない。
4. パイプラインの障害点が1つ減る。外部APIへの依存がなくなり「止まらない」に寄与する。

**トレードオフ（承知のうえで受け入れる）:**

一覧に並ぶのは **英語の description + 日本語の警告・ラベル**になる。
「日本語で読める」という価値は、要約文ではなく
**警告表示・ライセンス区分・判定理由**の日本語化で担保する。

**例外:** 週次サマリ（§13 Phase 2）は人間が執筆する。
その執筆過程で Claude Code を対話的に使うのは自由。
これは「パイプラインでLLMを呼ぶ」こととは別であり、
成果物には人間のレビューが入るため §2.3 S3 の要件も満たす。

### 9.2 構成

| レイヤ | 技術 | 理由 |
|---|---|---|
| 言語 | **TypeScript** | Astro と揃え、データモデルの型定義を収集・判定・表示で共有する |
| サイト生成 | **Astro** | 静的出力・zero-JS by default。Content Collections でデータ駆動のページ生成が得意 |
| ホスティング | **Cloudflare Pages** | 帯域無制限・ビルド500回/月の無料枠 |
| データストア | **JSON をリポジトリにコミット** | 個人規模ならDB不要。差分がGit履歴に残る |
| バッチ実行 | **GitHub Actions（cron）** | パブリックリポジトリなら無料 |
| OGP画像 | Satori 等 | 個別ページのSNS流入用 |

|---|---|
| GitHub API | **$0**（認証で5,000req/時） |
| GitHub Actions | **$0**（パブリックリポジトリ） |
| Cloudflare Pages | **$0**（無料枠内） |

### 9.4 ディレクトリ構成 ★v0.4 で確定

```
repo/
├─ .github/workflows/
│   └─ daily.yml                    # cron: 毎日 21:00 UTC (06:00 JST)
├─ scripts/
│   ├─ collect.ts                   # GitHub API から取得
│   ├─ evaluate.ts                  # 機械判定（フラグ・スコア・index判定）
│   └─ lib/
│       ├─ github.ts                # APIクライアント（レート制限対応・§10.2）
│       ├─ categorize.ts            # ルールベース分類（§6.3）
│       └─ flags.ts                 # 警告フラグ判定（§7.1）
├─ data/
│   ├─ repos/
│   │   └─ {owner}/{name}.json      # ★1リポジトリ1ファイル
│   └─ snapshots/
│       └─ YYYY-MM-DD.json          # ★1日1ファイル
├─ src/                             # Astro
│   ├─ types.ts                     # ★データモデル定義（§6）。scripts と共有
│   ├─ pages/
│   ├─ components/
│   └─ layouts/
├─ docs/SPEC.md                     # この文書
└─ package.json
```

**設計判断の理由:**

| 判断 | 理由 |
|---|---|
| **1リポジトリ = 1ファイル** | 全件を1つのJSONに入れると、1件の変更で毎日ファイル全体が書き換わり、Git差分が巨大になる。分割すれば変更分だけが差分に出る |
| **スナップショットは日付ごと** | 追記型のデータを1ファイルにすると際限なく肥大化する。日付分割なら1日1ファイル追加されるだけ |
| **単一リポジトリに集約** | データ更新とサイトビルドを Actions 内で連続実行できる。分けると連携が煩雑 |
| **`src/types.ts` を共有** | データモデルを1箇所に定義し、収集・判定・表示すべてで型を効かせる |

### 9.5 ビルド時間の監視 ★v0.4 で追記

**Cloudflare Pages のビルドは20分でタイムアウトする。**

個別ページが増えるとAstroのビルド時間が伸びるため、以下を監視する。

- 生成ページ数が **1,000 を超えたらビルド時間を計測する**
- ビルドが **10分を超えたら**対策を検討（古い日次アーカイブの生成除外、増分ビルド等）

現時点（1日5〜15ページ生成）では2〜3ヶ月は問題にならない見込み。

## 10. データ取得方針

### 10.1 原則と認証 ★v0.3 で確定

**主データは GitHub REST API（公式経路）から取得する。**

**認証は Personal Access Token (PAT) を使用し、リポジトリ Secrets に登録する。**

| 認証方法 | 上限 | 採用 |
|---|---|---|
| 未認証 | 60 req/時 | ✕ |
| **PAT** | **5,000 req/時** | ✅ **これを使う** |
| GitHub Actions の `GITHUB_TOKEN` | 1,000 req/時/repo | ✕（将来の件数増に対応できない） |

### 10.2 レート制限への配慮 ★v0.3 で追記

GitHub には副次的な制限がある。**実装時に必ず考慮すること。**

- 同時リクエストは REST/GraphQL 合わせて **100まで**
- REST API は **毎分900ポイント**（GET は1ポイント）

**実装要件:**
- **`Promise.all` で全件を一括並列実行しないこと**
- 同時実行数を **5〜10 程度に制限**する（p-limit 等）
- `X-RateLimit-Remaining` ヘッダを監視し、枯渇時は待機
- 429 / 403 応答時は指数バックオフ

> Claude Code に実装させる場合、指示しないと素直に `Promise.all` を使う。
> このセクションを明示的に読ませること。

### 10.3 Trending ページの扱い

GitHub Trending には **公式APIが存在しない**（HTMLスクレイピングのみ）。
かつ約6時間ごとに再計算され、ランキングアルゴリズムは非公開。

**したがって Trending は「補完データ」に位置づけ、必須依存にしない。**

| 理由 | 内容 |
|---|---|
| 安定性 | HTML構造が変われば即座に壊れる。ここに依存すると「毎日止まらない」が崩壊する |
| 規約 | GitHub利用規約はスクレイピングを限定的に許可。低頻度なら実務上問題になりにくいが、リスクはゼロではない |

**実装要件:**
- 取得は **1日1回のみ**
- 失敗時は前日キャッシュにフォールバックし、サイト更新は止めない
- スクレイパ破損の検知と通知
- 主軸は GitHub Search API（`created:>{date} sort:stars` 等）

> **注記:** 「Claude Code に収集させるからスクレイピングではない」は成立しない。
> 実行主体がAIであっても、GitHub側から見れば同じ自動アクセスである。
> 判断基準は「実行主体が何か」ではなく「頻度・規模・公式経路の有無」。

### 10.4 追跡対象の管理 ★v0.5 で確定

偽スター判定はスター推移を必要とするため、**一度検知したリポジトリは継続的に追跡する**。
追跡対象は日々増えるので、上限と更新頻度を定める。

#### 上限

**追跡対象の上限は 1,000 件とする。**

| 判断 | 理由 |
|---|---|
| 1,000件 | API枠（5,000req/時）に対して安全。実行時間2〜3分。トレンド系はほぼカバーできる |
| 3,000件以上にしない | 初日にAPI枯渇で失敗すると、データが1件も貯まらない。まず確実に動かす |
| 少なめで始めない | **追跡をやめた期間のスター履歴は永久に欠損する。後から遡れない** |

> 増やすのは設定値の変更だけで済むが、欠損したデータは戻らない。
> 1ヶ月運用してAPI消費の実測が出てから増減を判断する。

#### 3層構造

全件を毎日同じ頻度で見に行く必要はない。以下の3層に分ける。

| 層 | 条件 | 件数目安 | 更新頻度 |
|---|---|---|---|
| **ホット** | 直近30日に検知 or スター増加中 | 200〜300 | **毎日** |
| **通常** | 上記以外の追跡対象 | 700 | 3日に1回 |
| **休眠** | 90日以上スターがほぼ動いていない | — | 週1回。または追跡停止 |

これにより1日の実リクエストは **300〜500件程度**に収まる（枠の1割以下）。
**スター急増を検出したいのはホット層のみ**なので、判定精度は落ちない。

#### 初期シード（Phase 0 初日）

```
# 新しめで勢いのあるもの
created:>{1年前} stars:>200 sort:stars        → 上位500件

# 定番だがトレンドに再登場しうるもの
stars:>5000 pushed:>{60日前} sort:stars       → 上位500件
```

#### ⚠️ Search API の1,000件制限

**GitHub Search API は1クエリあたり最大1,000件しか返さない。**
それを超えて取得するには、条件でレンジ分割する必要がある。

```
stars:200..500
stars:500..1000
stars:1000..5000
stars:>5000
```

**実装時に必ず考慮すること。** 分割せずに書くと、静かに上位1,000件で打ち切られ、
「なぜか件数が増えない」という気づきにくいバグになる。

### エラー時の原則

**「止まらないこと」が差別化なので、部分的な失敗でサイト更新は止めない。**

| 失敗箇所 | 挙動 |
|---|---|
| Trending取得失敗 | 前日キャッシュを使用。Search APIの結果のみで続行 |
| 一部リポジトリ取得失敗 | スキップして続行 |
| レート制限到達 | 待機してリトライ。ダメなら取得済み分だけで続行 |
| 全体失敗 | 前日のサイトを残し、Discordに通知 |

### 12.1 構造化データ

| 型 | 使用 | 備考 |
|---|---|---|

- OGP画像の自動生成
- noindex の適用（§2.5）
- Core Web Vitals: LCP 2.5秒未満を目標

### 12.3 狙う検索クエリ

| クエリ | 勝算 | 理由 |
|---|---|---|
| 「{repo名} ライセンス」「{repo名} 商用利用」 | **高** | 本サイトの独自データが検索意図に完全一致。競合が薄い |
| 「{repo名} とは」「{repo名} 使い方」 | 低 | Qiita / Zenn / 公式ドキュメントが強い。単なる翻訳では勝てない |
| 「{repo名} 日本語」 | 中 | 日本語READMEの有無を出せるのは強み |
| 「GitHub 偽スター」「スター 買われている」 | **高** | `/flagged` と `/about/criteria` で狙う。日本語の解説が存在しない |

> v0.2 にあった「{repo名} 危険」は削除。検索需要が薄く、
> かつ特定リポジトリを「危険」と断定する表現は名誉毀損リスクを伴うため。

## 17. 運用ルール ★v0.3 で新設

> **前提: このサイトが失敗する最大の原因は技術ではなく「継続できないこと」。**
> 競合Bは機能的には十分作り込まれているが、2週間更新が止まっている。
> 以下は「意志で頑張る」のではなく「仕組みで守る」ためのルール。

### 17.1 人間がやること／自動でやること

| 処理 | 実行者 | 頻度 | 所要時間 |
|---|---|---|---|
| データ収集・スナップショット保存 | **自動** | 毎日 | 0分 |
| 機械判定（フラグ・スコア） | **自動** | 毎日 | 0分 |
| 一覧・個別ページの生成 | **自動** | 毎日 | 0分 |
| サイトのビルド・デプロイ | **自動** | 毎日 | 0分 |
| 手動コメント（注目枠） | 人間 | **週1〜2回** | 15分 |
| 週次サマリの執筆 | 人間 | **週1** | 30分 |
| Search Console の確認 | 人間 | **週1** | 5分 |

**人間の作業は合計で週1時間以内に収める。これを超える設計は却下する。**

> v0.2 では「注目5〜10件に手動コメント」を毎日行う前提になっており、
> 「人間の作業は週1」という記述と矛盾していた。v0.3 で修正。

### 17.2 止まらないための仕組み

| # | 仕組み | 目的 |
|---|---|---|
| 1 | データ収集と公開の完全自動化 | 人間が1ヶ月放置してもサイトは更新され続ける |
| 2 | 失敗時の Discord 通知 | **気づかないまま止まっているのが最悪**。競合Bの状態 |
| 3 | 部分失敗でも止めない設計（§11） | 1箇所の失敗で全体が止まらない |
| 4 | 人間の作業を週1時間以内に固定 | 忙しい週でも飛ばせる規模に保つ |
| 5 | 手動コメントは「任意」扱い | 書かなくてもサイトは成立する（注目枠を空にできる） |
| 6 | **結果の監視（下記）** | **エラーを出さずに静かに止まるケースを拾う** |

#### 結果の監視 ★v0.5 で追加

> **前提: 外部サービスに依存するものは、自分が何もしなくても壊れる。**
> 壊れること自体は防げない。**気づかないまま数週間経つこと**が致命的である。

「処理の失敗」を検知するだけでは不十分。**エラーを出さずに止まるケース**があるため、
**結果そのもの**を監視する。

| 監視項目 | 条件 | 通知 |
|---|---|---|
| データの鮮度 | 最新スナップショットが **2日以上前** | ⛔ 即通知 |
| 取得件数 | 前日比で **50%以上減少** | ⚠ 通知 |
| 新規検知数 | **3日連続で0件** | ⚠ 通知 |
| ビルド時間 | **10分超過**（§9.5） | ⚠ 通知 |

**「データの鮮度」の監視が最も重要。**
処理の成否ではなく結果を見るため、想定していない壊れ方も拾える。

実装は日次パイプラインとは別の軽量ワークフローにする
（パイプライン自体が動かなくなった場合に検知できないため）。

#### 想定される「勝手に壊れる」パターン

| # | 原因 | 対策 |
|---|---|---|
| 1 | GitHub API のレスポンス構造変更 | パースエラーで該当件のみスキップ。通知 |
| 2 | GitHub の障害 | 前日キャッシュ。翌日リトライ |
| 3 | 追跡対象増加でレート制限到達 | §10.4 の上限。取得件数の監視 |
| 4 | Trending の HTML 構造変更 | §10.3 フォールバック |
| 5 | 依存パッケージの破壊的変更 | **バージョンを固定する（`npm ci` + lockfile コミット）** |
| 6 | ビルド時間の20分超過 | §9.5 |
| 7 | **Actions の cron が発火しない／遅延する** | **GitHub Actions のスケジュール実行は混雑時に遅延・スキップされる仕様。データ鮮度の監視で拾う** |

### 17.3 期待値の設定

**最初の3〜6ヶ月はアクセスも収益もほぼゼロ。これが正常。**

SEO が効き始めるまで時間がかかるため、「頑張っているのに誰も来ない」期間が必ず来る。
ここで折れるのが最も多い失敗パターン。

**アクセス以外の進捗指標を持つこと:**

- スナップショットの蓄積日数（毎日1ずつ増える。何もしなくても増える）
- 検知した警告つきリポジトリの累計数
- 偽スター判定の精度（実際に消えたリポジトリと突き合わせる）

これらは**アクセスがゼロでも増え続ける**ため、モチベーションの支えになる。

### 17.4 やらないことリスト

以下は「やりたくなるが、継続を壊すのでやらない」。

- 毎日ブログ記事を書く
- 全リポジトリに手動でコメントをつける
- デザインの作り込み（Phase 3 以降）
- SNS への毎日の投稿
- 機能追加（Phase の順序を守る）
