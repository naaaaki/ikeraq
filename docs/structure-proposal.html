サイト構成とページのかたち

競合2サイトを調べたうえで、Ikeraq のURL設計と、個別ページのテンプレートを提案します。結論を先に言うと、競合はどちらも「読んで終わり」で止まっていて、「使い始めるまで」を書いていません。ここが空いています。

調べたこと

競合A — GitHub トレンド日本語解説

今日／週間のタブと言語フィルタ。1行の要約、スター数、今日の急上昇、fork、タグを並べた一覧サイトです。

穴：個別ページが存在しません。各リポジトリは GitHub へ直リンクするだけなので、「{repo名} 使い方」のような検索で拾える受け皿がありません。収益はリポジトリごとの Udemy 広告です。

競合B — ghtrend

こちらは作り込まれています。トップ・日別・個別ページ・殿堂入り・週間まとめの5種類。各リポジトリに、キャッチーな見出し／3〜5文の要約／使える場面の具体例／なぜ今話題か／注目ポイント2つ／対象レベル（初心者・中級・上級）を生成しています。

穴：全自動です。毎日スクレイピングして LLM に全件書かせているため、作者自身が「たまに何故か英語で出力されちゃう」と書いています。品質が安定せず、Google が問題視する「大量生成」にも近い形です。

両方に共通して無かったもの

  • 使い始めるまでの手順。「何ができるか」は書いてあっても、「で、どう入れるの」が無い
  • 日本語 README があるかどうか。日本語圏向けサイトなのに、両方とも出していません
  • 人の言葉。触った人が「ここが効く／ここは合わない」と書いた文章がない

どこで勝つか

1. 数は少なく、中身を濃く

全件に紹介文を付けない。週3〜5本でいいので、Naoki が読んで確認した文章だけ載せる。競合Bの弱点（精度が不安定・大量生成）の裏返しです。

2. 使い始めるまでを1画面に

導入コマンドと最小の動く例まで置く。両競合に無く、検索意図（「{repo名} 使い方」）にも一致します。

3. 蓄積データを見せる

毎日のスター記録は、日が経つほど競合が追いつけなくなる資産です。殿堂入り・推移グラフ・先週との比較で使います。

4. 日本語で読める度合い

日本語 README の有無を出す。実装済みなのに、まだ見せ場を作れていません。絞り込み条件にもします。

追加した2つの理由

  • /hall-of-fame — 毎日の記録があって初めて作れるページです。競合Bもやっており、有効性は確認済み。「今日たまたま伸びた」ではなく「ずっと注目されている」を示せます
  • /japanese — 日本語圏サイトの存在理由に直結します。データは既に取れています

個別ページのテンプレート

2種類あります。紹介文を書いたページと、書いていないページです。同じ型で作ると、中身の薄いページが量産されて検索エンジンに嫌われます。

A. 紹介文を書いたページ

上から下への順序そのものが設計です。読む人は「これ何？ → 自分に関係ある？ → どう使う？」の順に知りたがります。

  1. パンくず
    ホーム / カテゴリ / リポジトリ名
  2. リポジトリ名と、英語の説明文
    英語は小さく薄く。原文として残すが、主役にはしない
  3. 日本語の見出し一文
    「何ができるか」を一言で。ここだけ読んで離脱しても価値が残る形にする
  4. バッジ列
    言語 / ライセンスと商用可否 / スター数 / 最終更新 / 日本語READMEの有無
  5. どういうものか（3〜5段落）
    ★ページの主役。人が書く。英語の直訳にしない
  6. こういうときに効く
    具体的な場面を1〜2つ。「何ができるか」より「いつ使うか」のほうが読者の役に立つ
  7. 使い始める
    ★競合に無い。導入コマンドと、最小の動く例。ここまで書ければ「使い方」の検索を取れる
  8. 気をつける点
    ライセンス・メンテ状況を文章で。スコアの数字パネルは置かない
  9. 注目度の推移
    Ikeraq が記録しているグラフ。他所には無いデータ
  10. 基本情報
    fork / Issue / 貢献者 / リリース / 作成日。表で淡々と
  11. 似たもの・関連
    同じカテゴリの中から。回遊してもらう導線
  12. 出典と免責
    GitHub への正規リンク、書いた人、書いた日
「使い始める」を書くときの注意。README のコード例をそのまま貼るのは避けてください。README はコードとは別に、そのリポジトリのライセンスに従います。ライセンス未設定の README は全権利留保です。導入コマンド1行は事実に近いので問題ありませんが、使用例は自分で書いたものにしてください。抜粋の上限は500字です（仕様書 §8.2）。

B. 紹介文を書いていないページ

自動生成されるページです。Aの短縮版にしない。「本文が空っぽの記事」に見えると、検索エンジンから中身の薄いページと判断されます。最初からデータを見せるページとして組みます。

  1. リポジトリ名と、英語の説明文
    翻訳はしない。原文のまま
  2. バッジ列
    Aと同じ
  3. 注目度の推移
    ★このページの主役。7日分たまっていなければページ自体を検索エンジンに載せない
  4. 基本情報と気をつける点
    機械的に取得・判定したもの
  5. GitHub で見る
    深追いする人はここから原典へ

紹介文も警告も無く、推移も7日に満たないページは noindex にします。実装済みです。

決まったこと

2026年8月29日、Naoki の判断。詳細は docs/DECISIONS.md の D-005〜D-007。

紹介文は週3本。書ける週はそれ以上

3ヶ月で36本。特集を組める量になります。書けない週があってよい設計にします。トップは紹介文が1本も無い日でも成立させ、ピックアップ枠を出さずに一覧から始めます。書けない週にサイトが崩れる設計は、続きません。

「使い方」は入れる。ただし動かせたものだけ

導入コマンドと最小の動く例まで書きます。実際に動かせなかったら、その節ごと省きます。試していないのに手順を書くと、読者が動かせなかったときに信用がまとめて失われるためです。

GPU が要る・APIキーが要る・セットアップが重い、といったリポジトリは普通にあります。そういうものは「どういうものか」だけ書いて公開します。無理に埋めません。

特集は構成に含めない

特集はサイト構成ではなく、記事の作り方の話です。いまあるデータだけで作れるページが構成、書きためた記事が素材として要るページは構成外という線引きにしました。

後から足しても手戻りがありません。特集は「slug と、含めるリポジトリのIDを並べたファイル」を1つ足すだけで作れ、リポジトリのデータ構造には触らないためです。記事がたまってきたら、やりたければやる、という扱いにします。
