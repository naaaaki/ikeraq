## D-002 日本語の紹介文は Claude Code を使って人が書く（2026-08-29）

### 決定

- 日本語の紹介文は、**Naoki が Claude Code を対話的に使って**調査・執筆・翻訳する
- **日次パイプラインからは LLM を一切呼ばない**（仕様書 §9.1 は維持）
- 紹介文は `data/notes/{owner}/{name}.md` に置き、収集データとは分離して管理する

### 仕様書との関係

仕様書 §9.1 は「例外: 週次サマリは人間が執筆する。その執筆過程で Claude Code を
対話的に使うのは自由。これは『パイプラインでLLMを呼ぶ』こととは別であり、
成果物には人間のレビューが入るため §2.3 S3 の要件も満たす」としている。
D-002 はこの例外を、週次サマリだけでなく個別リポジトリの紹介文にも広げるもの。

したがって:

- ランニングコストは**ドメイン代のみ**のまま（API を叩かないため）
- パイプラインの障害点は増えない（外部依存が増えないため）
- 生成物の責任は運営者が負う（人のレビューが入るため）

### ★ 守らないと危険なこと

Google のスパムポリシー（仕様書 §2.1 が引用）は、scaled content abuse について
**「自動生成・人力・その両方の組み合わせのいずれであるかを問わない」**と明記している。
公式の該当例には「**人間によるレビューやローカライズなしに、自動翻訳のみでページ化する**」
が挙げられている。

**つまり「Claude Code で書いたから人力」は免罪符にならない。**

| # | ルール | 理由 |
|---|---|---|
| N1 | **全件に紹介文を付けない。** 書いたものだけ載せる | 大量・機械的な生成に見えた時点で該当する |
| N2 | **英語 description の直訳だけの紹介文を書かない**（仕様書 §2.3 S6） | 独自の価値がない |
| N3 | **必ず Naoki が読んでから公開する。** 生成したまま載せない | 誤情報の責任は運営者が負う |
| N4 | 紹介文の無いページは、警告・スコア・スター推移で独自価値を担保する | §2.3 S2 |

書く分量の目安は仕様書 §17.1 のとおり **週1〜2回・15分**。
これを超える運用は「継続できない設計」として却下する（§17 の前提）。

> 偽スターなんてみんな気にしてないから排除

### 廃止したもの

| 対象 | 内容 |
|---|---|
| `fake_star_suspicion` | 疑いの段階（なし/低/中/高） |
| `suspicion_signals` / `suspicion_provisional` | 判定の根拠と暫定フラグ |

### 残したもの

**実運用に耐えるかの判定は残す。** 廃止したのは「スター数が信用できるか」の軸だけ。

- 警告フラグ5種（`archived` / `stale` / `no_license` / `copyleft` / `thin_readme`）

- 判定基準の全公開（`docs/criteria.md`）

紹介サイトだからこそ、**紹介したものが業務で使えるか**を添える意味がある。

- スター推移の記録（`data/snapshots/`）は**引き続き必要**。
  偽スター判定のためではなく、**注目度の推移をグラフで見せるため**（SPEC §6.2 の資産性は変わらない）
- 仕様書 §7.2 / §7.3 / §7.5、§14 の失敗パターン10 は失効

### 判断が変わった場合

判定ロジックは Git 履歴（コミット `85e1931` 時点）に残っている。
復活させる場合はそこから戻せる。ただしスター履歴の蓄積は続いているため、
復活時点で過去に遡って判定できる。

## D-006 「使い方」は、実際に動かせたものだけ書く（2026-08-29）

### 決定

個別ページに **「使い始める」** の節を置く。導入コマンドと、最小の動く例まで書く。
ただし条件が付く。

> **実際に動かせたものだけ書く。動かせなかったら、その節ごと省く。**

Naoki の判断:

> 使い始めるって　使いかたってことだよね？　まず使えるものなのかしだいだけど　できるのであれば入れていきたい

### なぜ条件を付けるか

試していないのに手順を書くと、読者が動かせなかったときに信用がまとめて失われる。
紹介文の本数より、書いた内容に責任が持てることを優先する（D-002 N3 と同じ考え方）。

現実に、次のようなリポジトリは簡単には試せない。無理に埋めず、節ごと省く。

- GPU が必要なもの
- API キーや外部アカウントが必要なもの
- セットアップが重いもの（データベースのクラスタ構築など）

### ★ 著作権上の注意

README のコード例をそのまま貼らない。
README はコードとは別に、そのリポジトリのライセンスに従う。
ライセンス未設定の README は全権利留保である（仕様書 §8.2）。

| 書いてよいもの | 理由 |
|---|---|
| 導入コマンド1行（`npm install x` 等） | 事実に近く、著作物性が低い |
| **自分で書いた**最小の使用例 | Ikeraq の著作物になる |
| README からの抜粋（**最大500字**） | 仕様書 §8.2 の上限 |

### 競合との関係

調査した競合2サイトは、どちらも「使い方」を書いていない。
「{repo名} 使い方」の検索意図に応えられるのは、現状この節だけである。

## D-008 図は任意。型は決め打ちせず、実例から育てる（2026-08-29）★「任意」は D-010 で撤回

### 決定

- ~~**図は必須ではない。** 無理に入れない~~ → **D-010 で原則必須に変更**
- **図解は SVG で作る。** AI画像生成は使わない
- **型（フォーマット）を先に決めない。** 最初の5〜10本は毎回その場で作り、
  繰り返し出た形だけをあとからテンプレにする

Naoki の判断:

> ちょっとこの画像は課題だね、どうしていくかは ものによって違うだろうし

### なぜ型を先に決めないか

一度「流れ型・まとめ型・置き換え型・層型」の4つを決め打ちで作ったが、
**実例が1本もない状態での想像だった。** リポジトリの性格は幅が広く、
どの形が実際に繰り返し出るかは、書いてみるまで分からない。

D-007（特集）と同じ判断。**素材がない段階で設計しない。**

### なぜ AI画像生成を使わないか

参考にした形（見出し＋横並びのアイコンとラベル＋締めの一行）は、
**キャッチーさの源が文字そのもの**にある。AI画像生成は日本語を崩すため、
この形は原理的に作れない。

SVG なら:

| | SVG | AI画像生成 |
|---|---|---|
| 文字 | 正確（日本語も） | 崩れる |
| ブランド色 | `#1E5A48` がそのまま出る | 近い色になるだけ |
| ファイルサイズ | 1〜3KB | 200KB〜1MB |
| 修正 | 1語だけ直せる | 作り直し |
| 出来上がるまで | 一発 | 当たりが出るまで繰り返す |

ファイルサイズは SEO に直接効く（仕様書 §12.2 は LCP 2.5秒未満を要求）。
週3本・1本20分の制約でも、生成を繰り返す時間はない。

### ★ SVG はインラインで置く

ページのフォント（Zen Kaku Gothic New）を継がせるため、
`<img>` で読み込まず、HTML に直接書く。外部ファイルにすると
フォントが効かず、図だけ書体が変わって貼り付け感が出る。

### 図を入れないほうがいい場合

- 説明が箱ひとつで終わる（絵にすると情報がゼロになる）
- 見た目が主役のもの（UIツール・テーマ）→ スクリーンショットのほうがよい。
  ただし著作権の確認が要る
- 形が思いつかない → 無理に作らない

### AI画像生成を使う余地

図解では使わない。ただし**雰囲気を出すイラスト**（特集の表紙など）には
使える可能性がある。その時点で改めて考える。

## D-009 サイト本体は Astro 5 で作る（2026-08-29）

### 決定

- **Astro は 5 系を使う。** 最新の 7 系は採用しない
- **Windows のスマートアプリコントロールはオフにしない**

Naoki の判断:

> Astro 5 のまま進める

### なぜ最新版を使わないか

Astro 7 系のビルドは、署名のないネイティブバイナリ（`.node`）を実行する。
Naoki の PC は **スマートアプリコントロールが有効**（`VerifiedAndReputablePolicyState = 1`）で、
これがバイナリの実行を止める。ビルドも開発サーバーも起動できない。

WASM 版のバイナリに差し替える回避策も試したが、
パッケージの解決に失敗して同じく通らなかった（最小構成のプロジェクトでも再現）。

スマートアプリコントロールは、**一度オフにすると Windows を再インストールしない限り戻せない。**
サイトを1つ作るために、戻せない設定変更をする理由はないと判断した。

### 残るリスクと、それを許容した理由

Astro 5 には未修正の脆弱性報告が8件ある（修正されているのは 7 系のみ）。
そのうえで 5 系を選べるのは、報告されている攻撃経路を**1つも使っていない**ため。

| 報告されている経路 | Ikeraq での使用 |
|---|---|
| `define:vars` の `</script>` エスケープ漏れ | 使っていない |
| spread 属性名のエスケープ漏れ | 使っていない |
| `transition:*` / View Transitions | 使っていない |
| Server island のパラメータ | 使っていない（サーバーを持たない） |
| slot 名のエスケープ漏れ | 名前つき slot は `head` のみ。値は固定 |
| 事前生成エラーページの SSRF | 静的出力のみ |

**★ この前提が崩れたら、判断もやり直すこと。**
上の表にある機能を使いたくなったときは、先にこの決定を読み直す。

### 第三者が書いた文字列の扱い

GitHub の description・topics・README 抜粋は**第三者が書いた文字列**である。
これらを spread 属性や `define:vars` に渡さないこと。
通常の要素の中身として置く限り、Astro が自動でエスケープする。

### 将来の移行

WSL2 の上で開発すれば、設定を変えずに 7 系へ移れる。
Cloudflare Pages のビルドは Linux なので、本番側は最初から制約を受けない。
急ぐ理由が出たときに検討する。

## D-010 図解を原則必須にする（2026-09-01）

### 決定

**すべての記事に図解を入れる。** 入れない場合は、書いた側が理由を明示する。

D-008 の「図は必須ではない。無理に入れない」を**この点だけ差し替える**。
SVG で作ること・型を決め打ちしないことは D-008 のまま変えない。

Naoki の指示:

> すべての記事これから図解は必須にしてほしい　必要ない場合はそのうえで理由をおしえて

### なぜ変えたか

D-008 は「無理に入れない」という**書き手を守る規則**だった。
運用してみると、これは**作らない側に倒れやすい。** 図があるかどうかは
記事ごとに毎回考える必要があり、考えないと自動的に「無し」になる。

必須に倒すと、既定が反転する。**作らないほうに理由の説明が要る**ため、
「今日は思いつかなかった」で流れなくなる。

### 入れない場合の扱い

理由を言わずに省略しない。次の3つは、理由として認める。

| 理由 | 例 |
|---|---|
| 説明が箱ひとつで終わる | 単機能のライブラリ。絵にすると情報が減る |
| 見た目そのものが主役 | UIツール・テーマ。スクリーンショットのほうが正確 |
| 形が思いつかない | ★ただし、**思いつかない理由まで書く。**「流れが無く、並列の列挙しかない」など |

### 図にできるか迷ったときの見分け方

**流れ・変換・前後の対比があるか**を見る。
「A が B を通って C になる」と言えるなら図にできる。
「A と B と C がある」だけなら、それは箇条書きで足りる。

## D-011 殿堂入りの条件を、伸びから累積に変える（2026-09-07）

### 決定

殿堂入りの条件を、**スターとフォークの両方で上位100位以内**に変更する。
毎日の順位（トレンド上位に入った日数）は使わない。

Naoki の判断:

> 殿堂入りは伸びを見るより　スターの数
> じゃあ　足さずに　フォークの上位とスターの上位　でとるか

### 何が問題だったか

旧条件は「その日のスター増加の上位50位に3日以上入った」で、58件が出ていた。

| # | 問題 | 実測 |
|---|---|---|
| 1 | 記録が9日しかないのに3日で通る | 3分の1入っただけで殿堂入り |
| 2 | ★ **順位をつける母数が日ごとに違う** | 8/31 は150件中の50位（上位33%）、9/7 は1000件中の50位（上位5%） |
| 3 | 落ち続けているものが残る | `Osmantic/ODS` は最初の3日だけ上位で、あと5日は108位→236位 |

2 が最も重く、**58件のうち44件が母数の少なかった時期（〜9/1）から追跡されていたもの**だった。
つまり「ずっと注目されている順」ではなく「早くから追跡対象に入っていた順」に近かった。

### なぜ足し算にしないか

スターは数十万、フォークは数万で桁がひとつ違う。合計で並べると
フォークがほとんど効かず、**スターだけの順位とほぼ同じ**になる。

- 上位30件のうち **27件が一致**（実測）
- 合計に占めるフォークの割合は平均 15%

「両方の上位に入っていること」を条件にすると、スターは高いがフォークが
極端に少ないもの（読まれただけのリンク集など）が落ちて、条件として意味を持つ。

**★ 半年後に「合計でいいのでは」と思ったら、この数字を先に見ること。**

### 結果

53件（うち紹介文つき5件）。並びは紹介文があるものが先、そのあとスターの多い順。

### 副作用

- `HALL_OF_FAME_DAYS` は削除した
- `TREND_RANK` と `trendDays` は**集計だけ残す**。どのページにも出していないが、
  毎日の記録は後から作り直せないため（SPEC §10.4）。将来の週次まとめで使う
- 母数が `HALL_OF_FAME_TOP * 2` 未満のときは0件を返す。
  データを入れ直した直後は全件が「上位100位」に入ってしまうため

### ★ 一度入ったものが、後から消える

旧条件は一度満たせば永久に満たしたままだった（日数は減らない）。
新条件は「いまの上位100位」なので、追い越されると外れる。
「殿堂入り」という言葉は普通「一度入ったら残る」と読まれるので、
ページに「いまの集計です」と添えてある。永続にしたくなったら、記録を1本増やす話になる。

> 今日　も　今日のトレンドに変えて　殿堂入りは　普通のトレンドに変えよっか

### ★ なぜ理由を書くのをやめたか（この決定の核心）

D-011 で条件をスター×フォークにしたとき、`docs/criteria.md` とページに
次の説明を書こうとしていた。

> スターは読まなくても押せますが、フォークは中身に手を入れようとした人しか押しません。
> **読まれただけのもの**と**実際に使われてきたもの**は、この2つの差に出ます。

**これは実際の結果と逆だった。** レビューで実データを数えて判明した。

| | |
|---|---|
| フォーク条件で**落ちた**もの | `rust-lang/rust`（フォーク115位）`microsoft/TypeScript`（133位）`ollama/ollama`（101位）`fastapi/fastapi`（226位）`neovim/neovim`（340位）`tailwindcss`（426位）ほか47件 |
| **残った**リンク集・教材 | `github/gitignore`（フォーク**2位**）`sindresorhus/awesome` `free-programming-books`（6位）`vinta/awesome-python` |

リンク集や教材は**項目を1つ足すためにフォークされる**ので、フォークが極端に多い。
完成品のソフトウェアは、使うだけならフォークされない。**因果が逆だった。**

判定根拠の公開はこのサイトの前提（CLAUDE.md 守ること #3）。
**根拠の説明が、そのすぐ下の一覧に反証されている**のは最も悪い形になる。

**★ 確かめていない因果を判定基準のページに書かない。** 条件だけを書き、
「フォークが多い＝よく使われている、ではありません」と明示した。

### なぜ「殿堂入り」をやめたか

Naoki の指摘は「作られたばかりのものしか取っていないのに、その中での殿堂入りはおかしい」。
実データで確認すると、追跡1,000件の内訳は **5年以上前のものが636件**で、
「作られたばかりばかり」ではなかった。ただし別の理由で言葉が合っていない。

| # | 理由 | 実測 |
|---|---|---|
| 1 | 一度入っても残らない | 条件が「いまの上位100位」なので、追い越されると外れる |
| 2 | 新しいものが入る | 53件中8件が1年未満。最新は **24日前**に作られた `deepseek-ai/deepseek-harness`（スター21万） |
| 3 | 1,000件の中の話 | `rust-lang/rust` が入っていない一覧を「殿堂」とは呼べない |

「殿堂入り」は普通「一度入ったら残る」と読まれる。実態と合わない。

### 「今日のトレンド」と「トレンド」の違い

同じ語を使うが、見ている軸が違う。

| | 見るもの |
|---|---|
| **今日のトレンド**（`/`） | その日にスターがいくつ増えたか |
| **トレンド**（`/trend/`） | 積み上がったスターとフォークの大きさ |

### 副作用

- `hallOfFameItems` → `trendItems`、`HALL_OF_FAME_TOP` → `TREND_TOP` に改名
- `TREND_RANK` は名前が紛らわしくなるため `DAILY_TOP_RANK` に改名（役割は変えていない）
- `test/hall-of-fame.test.ts` → `test/trend.test.ts`
- **URL の変更は公開前だから無傷。** 公開後は変えられない

## D-013 紹介文を書いたものは別枠にし、押し出さない（2026-09-07）

### 決定

- **紹介文を書いたリポジトリは、追跡から絶対に押し出さない**
- **追跡の上限を「発見枠1,000 ＋ 紹介文の本数」にする**
- 母数を書くときは、**どう集めた件数なのかも一緒に書く**

Naoki の指摘（3つとも）:

> 1000件撮ってるけど　別時に記事は日々上げて　その記事がその1000件から外れることあると思うんだけど
> だから紹介分は1000件いじょうになりえるってことだよね
> Ikeraq が追跡している1,000件のうち　っていうと　固定された1000件ってイメージしちゃう

### 何が問題だったか

押し出しの条件は「休眠層かつ90日以上停滞」だけで、**紹介文の有無を見ていなかった。**
記事を書いたリポジトリも押し出されうる。

押し出しても `data/repos/` のファイルは消していないので、**ページと記事は残る。**
ただし更新が止まる。

| | 押し出し後 |
|---|---|
| 記事のページ・本文 | 残る（404にはならない） |
| スターの推移グラフ | **その日から止まる** |
| 「今日の増加」 | **出なくなる** |

読者には**なぜ止まったのか分からず、こちらにも気づく手立てがない。**

### なぜ「別枠」にするのか

記事つきを1,000件の枠の中で守ると、**記事が増えるほど新しいものを見つける力が落ちる。**

| | 発見に使える枠 |
|---|---|
| いま | 1,000 |
| 1年後（週3本＝年150本） | 850 |
| 3年後 | 550 |
| **6〜7年後** | **0（新規が1件も入らない）** |

そこで発見枠1,000は据え置き、記事つきはその外側に積む。
10年後でも 1,000 ＋ 1,500 = 2,500件。1日1,000件を147秒で回せている現状から見て余裕がある。
記事つきは伸びが止まると休眠層に落ち、**週1回しか見に行かない**ので負担はほぼ増えない。

### 「追跡している1,000件」という書き方をやめる

**固定された1,000件だと受け取られる。** 実際は毎日の検索で顔ぶれが入れ替わる。
母数を出すときは、必ず集め方（30日以内に作られたもの／7日以内に更新されたもの／スター200以上）
まで書く。`docs/criteria.md` に「どうやって集めているか」の節を新設した。

### ★ ページに出している数字は「追跡件数」ではない

トレンドページの母数は `site.repos.length`＝`data/repos/` のファイル数。
押し出したものも残るため、時間が経つと追跡件数より大きくなる。
**「追跡している」とは書かないこと。**

### 副作用

- `evictable()` に `human_note !== null` の除外を追加
- `trackingCapacity(repos)` を新設。`collect.ts` の枠判定はこれを使う
- テスト2件を追加（`test/lib.test.ts`）

| 仕様書 | D-014 |
|---|---|

もとは「**人が書いています。** 調べる過程で AI を使うことはありますが、
公開前に必ず運営者が読んで確認しています」だった。

**これは嘘だった。** 本文を AI が書き、人が確認している。順序が逆に書かれていた。

## D-015 作業前の取り込みを、手順の0番として固定する（2026-09-08）

### 決定

- 記事を書く前に **必ず `npm run sync`**（`git pull --rebase --autostash`）を実行する
- 「記事を書くときの流れ」の **0番** に置く。1番より前
- 取り込みをプッシュ直前に回さない

Naoki の指摘:

> なんで毎回競合起きてるの？　毎回fetch pullしてないんじゃん？

### 事実の確認（指摘のうち、当たっていた部分と外れていた部分）

| | 実際 |
|---|---|
| 「毎回競合が起きている」 | **起きていない。** 71コミット中、マージは1件（2026-09-08）。内容の競合は履歴上ゼロ |
| 「pull していない」 | **当たっている。** 作業開始時ではなく、プッシュ直前に実行していた |

2026-09-08 に起きたのは競合ではなく、**未コミットの変更を抱えたまま pull した**
ことによる中断（`Please commit your changes or stash them`）だった。

### なぜ、このリポジトリでは特に危ないか

**毎朝6時（JST）に bot が `data/` を書き換えてコミットする**（`daily.yml`）。
朝以降に作業を始めた時点で、リモートは必ず1コミット先行している。

さらに悪いことに、**触るファイルが人と bot で重なる。**
記事を書くと `npm run evaluate` が `data/repos/*.json` を書き換えるが、
これは bot が毎日書き換えているファイルそのもの。

2026-09-08 の実測:

| | ファイル数 |
|---|---|
| bot のコミット（`adf77c4b`） | 1,033 |
| こちらのコミット（`0049a86b`） | 11 |
| **両方が触ったファイル** | **6（こちらが触った JSON の全部）** |

このときは行が違ったため自動でマージできた。だが `stars` のように
**bot と evaluate の両方が書く行**を人が触れば、そのまま競合になる。
競合するのが JSON だと、手で直す作業は事故を招きやすい。

### なぜ `--rebase --autostash` か

| 選択 | 理由 |
|---|---|
| `--rebase` | 分岐と合流の履歴を残さない。`daily.yml` の bot も同じく `--rebase` を使っている |
| `--autostash` | 書きかけがあっても止まらない。2026-09-08 の中断はこれで防げた |

### なぜ npm script にしたか

Fabrica 共通ルールには、すでに「作業を始める前に必ず `git pull`」と書いてある。
**書いてあっても守られなかった。** 文章を足しても同じことが起きる。

打てるコマンドとして手順表の中に置き、`npm run note` の前に並べた。
**守るべきことを、実行できる形にした**という変更になる。
