## D-001 コンセプトを「紹介」に変更（2026-08-29）

### 決定

サイトのコンセプトを次のとおりとする。

> **GitHub で注目を浴びている、面白いリポジトリを日本語で紹介するサイト**

### 仕様書との違い

仕様書 §1.2 は「**偽スターを見抜く**、日本語のGitHubトレンド」と定義し、
「偽スター警告こそが本サイトの存在理由」「日本語ラベルだけでは勝てない」としていた。

| | 仕様書 §1.2 | D-001 |
|---|---|---|
| 主役 | 偽スターの警告 | リポジトリの紹介 |
| 警告の位置づけ | サイトの存在理由 | 判断材料のひとつ |
| `/flagged` | 目玉ページ | 一機能 |

### 差別化をどこで取るか

仕様書 §1.2 は「差別化の三層」の第1層（偽スター警告）を存在理由としていた。
D-001 では、差別化は **日本語の紹介文**（D-002）で取りに行く。

## D-002 日本語の紹介文は Claude Code を使って人が書く（2026-08-29）

### 決定

- 日本語の紹介文は、**Naoki が Claude Code を対話的に使って**調査・執筆・翻訳する
- **日次パイプラインからは LLM を一切呼ばない**（仕様書 §9.1 は維持）
- 紹介文は `data/notes/{owner}/{name}.md` に置き、収集データとは分離して管理する

### 仕様書との関係

仕様書 §9.1 は「例外: 週次サマリは人間が執筆する。その執筆過程で Claude Code を
対話的に使うのは自由。これは『パイプラインでLLMを呼ぶ』こととは別であり、
成果物には人間のレビューが入るため §2.3 S3 の要件も満たす」としている。
D-002 はこの例外を、週次サマリだけでなく個別リポジトリの紹介文にも広げるもの。

したがって:

- ランニングコストは**ドメイン代のみ**のまま（API を叩かないため）
- パイプラインの障害点は増えない（外部依存が増えないため）
- 生成物の責任は運営者が負う（人のレビューが入るため）

### ★ 守らないと危険なこと

Google のスパムポリシー（仕様書 §2.1 が引用）は、scaled content abuse について
**「自動生成・人力・その両方の組み合わせのいずれであるかを問わない」**と明記している。
公式の該当例には「**人間によるレビューやローカライズなしに、自動翻訳のみでページ化する**」
が挙げられている。

**つまり「Claude Code で書いたから人力」は免罪符にならない。**

| # | ルール | 理由 |
|---|---|---|
| N1 | **全件に紹介文を付けない。** 書いたものだけ載せる | 大量・機械的な生成に見えた時点で該当する |
| N2 | **英語 description の直訳だけの紹介文を書かない**（仕様書 §2.3 S6） | 独自の価値がない |
| N3 | **必ず Naoki が読んでから公開する。** 生成したまま載せない | 誤情報の責任は運営者が負う |
| N4 | 紹介文の無いページは、警告・スコア・スター推移で独自価値を担保する | §2.3 S2 |

書く分量の目安は仕様書 §17.1 のとおり **週1〜2回・15分**。
これを超える運用は「継続できない設計」として却下する（§17 の前提）。

## D-004 偽スター判定を廃止（2026-08-29）

### 決定

**偽スターの検出・表示を、機能ごと廃止する。** 判定コードも削除した。

Naoki の判断:

> 偽スターなんてみんな気にしてないから排除

### 廃止したもの

| 対象 | 内容 |
|---|---|
| `fake_star_suspicion` | 疑いの段階（なし/低/中/高） |
| `suspicion_signals` / `suspicion_provisional` | 判定の根拠と暫定フラグ |
| 偽スター系フラグ5種 | `star_spike` / `low_activity` / `too_new` / `abnormal_fork_ratio` / `duplicate_suspect` |
| `scripts/lib/similarity.ts` | 類似名の突き合わせ |
| `scripts/verify-dependents.ts` | `dependents_count` の取得可否検証 |
| `dependents_count` | 「実利用の欠如」判定の専用フィールド |
| `/flagged` | 警告つき一覧ページ |

### 残したもの

**実運用に耐えるかの判定は残す。** 廃止したのは「スター数が信用できるか」の軸だけ。

- 警告フラグ5種（`archived` / `stale` / `no_license` / `copyleft` / `thin_readme`）
- `usability_score`（0〜100）
- 判定基準の全公開（`docs/criteria.md`）

紹介サイトだからこそ、**紹介したものが業務で使えるか**を添える意味がある。
ライセンスとメンテ状況は、読者が実際に判断に使う情報である。

### 副作用

- フラグの「2軸」構造が不要になったため、`Flag` から `axis` を削除した
- スター推移の記録（`data/snapshots/`）は**引き続き必要**。
  偽スター判定のためではなく、**注目度の推移をグラフで見せるため**（SPEC §6.2 の資産性は変わらない）
- 仕様書 §7.2 / §7.3 / §7.5、§14 の失敗パターン10 は失効

### 判断が変わった場合

判定ロジックは Git 履歴（コミット `85e1931` 時点）に残っている。
復活させる場合はそこから戻せる。ただしスター履歴の蓄積は続いているため、
復活時点で過去に遡って判定できる。

## D-006 「使い方」は、実際に動かせたものだけ書く（2026-08-29）

### 決定

個別ページに **「使い始める」** の節を置く。導入コマンドと、最小の動く例まで書く。
ただし条件が付く。

> **実際に動かせたものだけ書く。動かせなかったら、その節ごと省く。**

Naoki の判断:

> 使い始めるって　使いかたってことだよね？　まず使えるものなのかしだいだけど　できるのであれば入れていきたい

### なぜ条件を付けるか

試していないのに手順を書くと、読者が動かせなかったときに信用がまとめて失われる。
紹介文の本数より、書いた内容に責任が持てることを優先する（D-002 N3 と同じ考え方）。

現実に、次のようなリポジトリは簡単には試せない。無理に埋めず、節ごと省く。

- GPU が必要なもの
- API キーや外部アカウントが必要なもの
- セットアップが重いもの（データベースのクラスタ構築など）

### ★ 著作権上の注意

README のコード例をそのまま貼らない。
README はコードとは別に、そのリポジトリのライセンスに従う。
ライセンス未設定の README は全権利留保である（仕様書 §8.2）。

| 書いてよいもの | 理由 |
|---|---|
| 導入コマンド1行（`npm install x` 等） | 事実に近く、著作物性が低い |
| **自分で書いた**最小の使用例 | Wakuru の著作物になる |
| README からの抜粋（**最大500字**） | 仕様書 §8.2 の上限 |

### 競合との関係

調査した競合2サイトは、どちらも「使い方」を書いていない。
「{repo名} 使い方」の検索意図に応えられるのは、現状この節だけである。

## D-007 特集は構成に含めない（2026-08-29）

### 決定

特集（テーマ別のまとめ）は **サイト構成に含めない。** 記事の作り方の話として扱う。
記事がたまってきたら、やりたければやる。**いま設計しない。**

Naoki の指摘:

> 特集もたまってきたらできたらやるけど　それってサイト構成に関係ないと思うんだけど

### 線引き

| | |
|---|---|
| **構成** | いまあるデータだけで作れるページ |
| **構成外** | 書きためた記事が素材として要るページ |

特集は後者。紹介文が15〜20本たまるまで素材がない。

### 後回しにしても手戻りがない理由

特集は「slug と、含めるリポジトリのIDを並べたファイル」を1つ足すだけで作れる。
**`Repository` のデータ構造には一切触らない。**
URL 空間 `/collections/` も他と衝突しない。
したがって、いま構成に入れておく必要は実際にない。

### やるとしたら（メモ・設計はしない）

- 月1本、多くても月2本まで。まとめ記事の大量生成は
  scaled content abuse（仕様書 §2.1）に近づく
- Wakuru にしか作れない切り口がある
  （「日本語 README があるAIツール」「今月ずっと伸び続けているリポジトリ」）

## D-008 図は任意。型は決め打ちせず、実例から育てる（2026-08-29）

### 決定

- **図は必須ではない。** 無理に入れない
- **図解は SVG で作る。** AI画像生成は使わない
- **型（フォーマット）を先に決めない。** 最初の5〜10本は毎回その場で作り、
  繰り返し出た形だけをあとからテンプレにする

Naoki の判断:

> ちょっとこの画像は課題だね、どうしていくかは ものによって違うだろうし

### なぜ型を先に決めないか

一度「流れ型・まとめ型・置き換え型・層型」の4つを決め打ちで作ったが、
**実例が1本もない状態での想像だった。** リポジトリの性格は幅が広く、
どの形が実際に繰り返し出るかは、書いてみるまで分からない。

D-007（特集）と同じ判断。**素材がない段階で設計しない。**

### なぜ AI画像生成を使わないか

参考にした形（見出し＋横並びのアイコンとラベル＋締めの一行）は、
**キャッチーさの源が文字そのもの**にある。AI画像生成は日本語を崩すため、
この形は原理的に作れない。

SVG なら:

| | SVG | AI画像生成 |
|---|---|---|
| 文字 | 正確（日本語も） | 崩れる |
| ブランド色 | `#1E5A48` がそのまま出る | 近い色になるだけ |
| ファイルサイズ | 1〜3KB | 200KB〜1MB |
| 修正 | 1語だけ直せる | 作り直し |
| 出来上がるまで | 一発 | 当たりが出るまで繰り返す |

ファイルサイズは SEO に直接効く（仕様書 §12.2 は LCP 2.5秒未満を要求）。
週3本・1本20分の制約でも、生成を繰り返す時間はない。

### ★ SVG はインラインで置く

ページのフォント（Zen Kaku Gothic New）を継がせるため、
`<img>` で読み込まず、HTML に直接書く。外部ファイルにすると
フォントが効かず、図だけ書体が変わって貼り付け感が出る。

### 図を入れないほうがいい場合

- 説明が箱ひとつで終わる（絵にすると情報がゼロになる）
- 見た目が主役のもの（UIツール・テーマ）→ スクリーンショットのほうがよい。
  ただし著作権の確認が要る
- 形が思いつかない → 無理に作らない

### AI画像生成を使う余地

図解では使わない。ただし**雰囲気を出すイラスト**（特集の表紙など）には
使える可能性がある。その時点で改めて考える。

## D-009 サイト本体は Astro 5 で作る（2026-08-29）

### 決定

- **Astro は 5 系を使う。** 最新の 7 系は採用しない
- **Windows のスマートアプリコントロールはオフにしない**

Naoki の判断:

> Astro 5 のまま進める

### なぜ最新版を使わないか

Astro 7 系のビルドは、署名のないネイティブバイナリ（`.node`）を実行する。
Naoki の PC は **スマートアプリコントロールが有効**（`VerifiedAndReputablePolicyState = 1`）で、
これがバイナリの実行を止める。ビルドも開発サーバーも起動できない。

WASM 版のバイナリに差し替える回避策も試したが、
パッケージの解決に失敗して同じく通らなかった（最小構成のプロジェクトでも再現）。

スマートアプリコントロールは、**一度オフにすると Windows を再インストールしない限り戻せない。**
サイトを1つ作るために、戻せない設定変更をする理由はないと判断した。

### 残るリスクと、それを許容した理由

Astro 5 には未修正の脆弱性報告が8件ある（修正されているのは 7 系のみ）。
そのうえで 5 系を選べるのは、報告されている攻撃経路を**1つも使っていない**ため。

| 報告されている経路 | Wakuru での使用 |
|---|---|
| `define:vars` の `</script>` エスケープ漏れ | 使っていない |
| spread 属性名のエスケープ漏れ | 使っていない |
| `transition:*` / View Transitions | 使っていない |
| Server island のパラメータ | 使っていない（サーバーを持たない） |
| slot 名のエスケープ漏れ | 名前つき slot は `head` のみ。値は固定 |
| 事前生成エラーページの SSRF | 静的出力のみ |

**★ この前提が崩れたら、判断もやり直すこと。**
上の表にある機能を使いたくなったときは、先にこの決定を読み直す。

### 第三者が書いた文字列の扱い

GitHub の description・topics・README 抜粋は**第三者が書いた文字列**である。
これらを spread 属性や `define:vars` に渡さないこと。
通常の要素の中身として置く限り、Astro が自動でエスケープする。

### 将来の移行

WSL2 の上で開発すれば、設定を変えずに 7 系へ移れる。
Cloudflare Pages のビルドは Linux なので、本番側は最初から制約を受けない。
急ぐ理由が出たときに検討する。
